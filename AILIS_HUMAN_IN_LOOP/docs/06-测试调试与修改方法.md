## 3. 安全修改流程

1. **确认生效路径**：桌面、Hosted Node、Python backend 或静态 UI。
2. **写行为假设**：输入、期望、失败、取消、审批、持久化。
3. **找调用链**：入口、实现、返回、UI 消费者和测试。
4. **先复现**：记录稳定步骤、日志、run/session id 和实际版本。
5. **最小修改**：不顺手重构无关模块。
6. **定向测试**：先覆盖改动最接近的契约。
7. **集成验证**：跑完整 turn/工具/语音链，不只测 helper。
8. **生产构建**：检查静态路径、资源和 bundle。
9. **检查 diff**：确认没有缓存、secret、截图和构建垃圾。
10. **更新学习副本**：重新 build/verify，让 manifest 对应新源码提交。

## 4. 对话系统调试

### 先分层定位

| 层 | 观察 |
| --- | --- |
| UI | click/submit 是否触发；message DOM 是否添加；busy 是否锁死 |
| ChatTTS | turn 是否创建；history 是否正确；是否被 cancel |
| Chat Service | runtime kind、sessionId、runId、API/Gateway 调用 |
| Hosted/Gateway | health、SSE event、run timeline |
| Harness/Runner | task 状态、iteration、model response、tool calls |
| Persona | final surface 是否有 text/speech/action |
| 返回 UI | 迟到事件是否被 runId 过滤；最终是否释放 busy |

### 常见问题

- UI 有用户消息但无回复：看 `fetchAssistantTurn*` promise、API response 和 progress bridge。
- 一直“思考中”：看 SSE 缓冲、final event、异常 `finally` 和 turn release。
- 回复重复：检查重连后 cursor、event 去重、同 session in-flight 和 fallback 是否双发。
- 新一轮收到旧结果：检查 `eventBelongsToRun`、activeRunId 和取消后的迟到事件。
- Persona 输出内部协议：检查 renderer 是否被绕过或 `text_is_persona_safe` 被错误设置。

## 5. TTS 与口型调试

### 必须记录的五个事实

1. 当前 speech mode：server / cosyvoice3 / native / off。
2. 实际 candidate：不是设置值，而是本轮真正成功者。
3. voice id/name：`speechSynthesis.getVoices()` 返回的真实条目。
4. speaking 生命周期：start、audio/utterance start、boundary/energy、end/error/cancel。
5. VRM 输入：external lip sync 还是 fallback，数值是否到达 `applyLipSyncValue()`。

### Chrome 原生语音

- voices 可能在页面加载后异步出现，要监听 `voiceschanged`。
- 持久化 id 在另一台机器/Chrome 版本可能不存在，要回退但告知实际选中项。
- 浏览器 autoplay/用户手势策略会影响首轮。
- `speechSynthesis.cancel()` 后旧 utterance 事件可能迟到，要以 turn/session 防串线。
- 原生 TTS 没有可靠 PCM，不能要求与服务器音频同等的能量对齐。

### 性能卡顿

先用 Performance/renderer stats 分辨：

- VRM/Three 渲染：阴影贴图、像素比、后处理、多灯、透明和每帧包围盒计算。
- 音频：Analyser 采样和频繁 DOM/event 更新。
- 流式文本：每 token 全量 markdown 渲染/scroll。
- 主线程：大 JSON、memory/search 或同步存储误跑在 renderer。
- 网络：SSE 事件过密或 payload 过大。

不要在没 profile 前只凭感觉降低帧率或关闭口型。

## 6. VRM、镜头、光照和阴影

改渲染时分别验证：

- camera target、position、FOV、角色 world bounds；
- desktop/mobile canvas 尺寸和 devicePixelRatio；
- directional light position 与 yaw；
- shadow camera bounds、map size、bias/normalBias；
- ground receiver 位置、透明度和 blending；
- VRM mesh cast/receiveShadow；
- 页面透明背景与 scene background。

脚看不见可能是相机 target/FOV/裁剪，也可能是容器高度；阴影奇怪可能是灯角度、
shadow camera、bias 或 receiver，而不是只改 opacity。

## 7. Agent 调试

按每次 iteration 做时间线：

```text
input package
→ model request settings
→ raw decision
→ validated decision
→ selected tool/args
→ approval/policy
→ observation
→ context changes
→ evidence state
→ next decision/final
```

关注：

- 模型真正看到了哪些 instructions/items/tools；
- tool call id 与 output call id 是否匹配；
- 失败是模型协议、Gateway、Runtime 还是外部服务；
- context budget 是否导致关键事实被压缩；
- exact answer/evidence guard 为什么拒绝 final；
- 重试是否改变策略，还是重复同一失败动作；
- max steps 是否因为无效进度循环。

日志中不要输出 API Key、邮件密码、完整 secret 或用户敏感文件。

## 8. Memory 调试

### 写入问题

- 事件是否先进入 raw ledger？
- curated memory 写入由什么策略触发？
- block/event/daily note 是否选对类型？
- sessionId/runId 是否正确？
- 原子写失败是否保留旧文件？

### 召回问题

- retrieval query 是否包含当前用户目标和必要历史？
- scorer 是否找到了目标块？
- Context Compiler section budget 是否把它裁掉？
- `contextMode` 是否正确？
- sanitize 是否误删正常内容，或漏掉 secret？
- Model Input Builder 是否真的加入 developer memory message？

### 遗忘问题

- forget 是删 event、block 还是 key？
- raw ledger 的审计保留策略与“用户遗忘”语义是否一致？
- secret 是否单独保留/删除？
- 缓存/快照是否同步失效？

使用临时 state 目录做测试，绝不拿真实用户记忆做破坏性试验。

## 9. 工具和权限调试

1. 打印/断言 normalized tool id 和 args（脱敏后）。
2. 检查 contract lookup 和 schema error。
3. 检查 permission profile 来源。
4. 检查 risk/approval evaluation。
5. 检查 adapter 是否支持当前平台。
6. 检查实际 I/O 与 timeout/cancel。
7. 检查 observation/error normalization。
8. 检查 evidence/artifact refs。
9. 检查 Persona 解释。

对于写操作，用临时目录和明确 target；对 email 用 draft/test account；对 computer use
用隔离测试窗口。

## 10. Hosted Runtime 调试

把问题拆成：

- 静态页面版本；
- API base/CORS/HTTPS；
- health/readiness；
- 创建 run；
- SSE cursor/缓冲/断线重连；
- Agent 核心；
- server tool/platform support；
- state persistence；
- final payload；
- 浏览器 TTS/VRM。

浏览器 Network、服务器 run timeline 和 commit/version 三者必须能对应。

## 11. 测试应覆盖的状态矩阵

对新功能至少考虑：

| 维度 | 值 |
| --- | --- |
| 结果 | success / partial / failure |
| 控制 | normal / cancel / timeout / max-steps |
| 权限 | allowed / approval / blocked |
| 配置 | ready / missing / invalid |
| 平台 | desktop / hosted / unsupported |
| 上下文 | fresh / resumed / compacted |
| 输出 | text / structured / artifact / image |
| 并发 | single / duplicate session / parallel safe |

不是每个功能都需笛卡尔积，但高风险交叉组合要明确。

## 12. Diff 与提交检查

```powershell
git status --short
git diff --check
git diff --stat
git diff
```

只 stage 预期路径。尤其排除：

- 浏览器 profile、缓存、截图；
- `.env`、key、token、Cookie；
- 临时 build tarball、日志；
- 真实 memory/state；
- 与本任务无关的用户未提交改动。

提交后再用远程 `ls-remote` 或 GitHub 核对目标 `main`，不要只看本地 commit。

## 13. 学习副本完整性验证

校验器执行三重对照：

1. 当前受跟踪源文件列表等于 manifest 列表；
2. 原文件 SHA-256 等于 manifest；
3. `source/` 副本 SHA-256 等于 manifest；
4. 每个文本文件存在非空 line guide；
5. `SNAPSHOT_COMMIT` 与 manifest 一致且是当前 HEAD 的祖先；
6. 八本文档都存在。

文本哈希采用 UTF-8/LF 规范化模式，避免 Git 在 Windows 的 CRLF checkout 让相同
源码产生不同哈希；二进制哈希始终使用原始字节。

若正式源码在 snapshotCommit 之后发生变化，先提交源码，再重建副本；不要手工修改
manifest 来掩盖差异。
