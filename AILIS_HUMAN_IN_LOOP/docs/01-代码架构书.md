# 01｜AILIS 代码架构书

## 1. 总体分层

```text
用户
  │
  ▼
页面与具身层（HTML / src / VRM / Chat / TTS）
  │  Electron preload IPC 或 Hosted HTTP/SSE
  ▼
宿主与边界层（electron/main / hosted runtime / gateway）
  │
  ├── Persona Surface：只负责用户可见表达
  └── System TaskAgent Harness：管理唯一任务代理
          │
          ▼
      Agent Runner：模型决策循环、上下文、证据、恢复
          │
          ├── Context / Prompt / Memory
          ├── Tool contract / router / runtime
          ├── Platform adapter / MCP / artifact
          └── audit / checkpoint / events
```

核心设计原则是：模型负责语义判断；确定性代码负责 schema、权限、预算、工具契约、
生命周期、持久化、审计和安全边界。不要用大量关键词分支偷偷替代一个本来合法的
模型决策。

## 2. 运行环境与代码归属

| 环境 | 主要文件 | 能力 |
| --- | --- | --- |
| 浏览器渲染进程 | `src/*.js`、HTML/CSS | DOM、VRM、音频、Web Speech、用户交互 |
| Electron preload | `electron/preload.cjs` | 在 context isolation 下暴露白名单 IPC |
| Electron 主进程 | `electron/main.cjs` | 窗口、协议、系统资源、IPC、Gateway、Agent、状态 |
| Agent 核心 | `electron/ailis-*.cjs` | TaskAgent、Memory、Context、Tool、Persona、审计 |
| Hosted Node | `scripts/start-ailis-hosted-runtime.cjs` 等 | 将核心能力通过 HTTP/SSE 服务给网页 |
| Python 后端 | `backend/` | 可选 FastAPI、模型/业务服务和兼容 API |
| 工程进程 | `scripts/`、`tests/`、`evals/` | 构建、资源准备、部署、测试、评测 |

`.cjs` 让核心宿主代码保持 CommonJS；前端和工程脚本主要用 ESM。跨边界时不要直接
传递不可序列化对象，应使用明确的 JSON 数据契约。

## 3. 页面与具身层

### 3.1 页面入口

- `index.html` / `about-ailis.html`：完整主界面及展示入口。
- `pet.html`：桌宠窗口的轻量 DOM。
- `control.html`：控制面板和运行时配置。
- `chat.html`：聊天独立界面。
- `agent-lab.html`：Agent 分析/实验界面。
- `Test/`：GitHub Pages/网页体验版相关入口和资产。

HTML 决定 DOM 和模块加载，真实状态与行为主要在 `src/`。改变一个元素 id 时要搜索
所有 `getElementById`、query selector、测试和 CSS。

### 3.2 `src/pet-app.js`

这是桌宠/角色装配入口。它建立 VRM 系统、聊天服务、语音提供器、音频播放器和交互，
调用 `vrmSystem.init()`、`loadModel()`，并在退出时释放指针、命中测试和语音资源。
它的职责是“接线”，不应塞入 Agent 策略。

### 3.3 `src/vrm-model-system.js`

`VRMModelSystem` 负责：

- Three.js renderer、camera、scene、light 和 shadow receiver。
- 加载 VRM 与 VRMA，初始化表情/动作，维护 idle、dance 和状态动作。
- 根据 Persona Surface 应用表情、动作、注视、情绪和强度。
- 计算角色屏幕包围盒，支持点击/拖拽命中。
- 管理说话状态、外部 lip-sync 值、平滑和模型口型表达。
- 在渲染循环中更新动画、眨眼、说话和场景 mood。

其中 `startAudioDrivenSpeech()` 表示口型由真实外部能量驱动；
`startFallbackSpeech()` 使用程序脉冲；`setLipSyncValue()` 接收外部采样；
`updateSpeaking()` 做目标值和平滑；`applyLipSyncValue()` 最终交给角色表情控制器。
排查“嘴不动/不对齐”必须沿这五处和音频提供器一起看，不能只改一个振幅常量。

### 3.4 `src/chat-tts-system.js`

`ChatTTSSystem` 是可见对话协调器，不是大模型本身。主要职责：

- 维护会话 id、浏览器/桌面历史、消息 DOM 和当前 turn。
- 发送用户消息，流式更新 assistant 文本，处理中断与 fallback。
- 从结果中提取 Persona Surface，触发表情、动作和 avatar speech 事件。
- 选择 chunked TTS、首选语音、fallback 语音，处理 autoplay 错误。
- 让 UI busy 状态、turn cancellation、audio playback 和角色 speaking 状态一致。

关键路径是 `sendMessage()` → `fetchAssistantTurn*()` →
`renderAssistantReply()` / streaming → `playPreferredSpeech()` →
`playFallbackSpeech()`。任何异常都必须最终释放 turn 和 speaking 状态。

### 3.5 `src/speech-provider.js`

这里有三类候选器：

- `ServerTTSCandidate`：向服务器请求音频。
- `CosyVoice3TTSCandidate`：调用 CosyVoice3，可支持分块。
- `NativeSpeechSynthesisCandidate`：使用 Chrome/浏览器 Web Speech。

`SpeechProvider` 负责编排候选、记录失败、创建分块会话和播放。
`createSpeechProvider()` 根据 mode、运行环境和 fallback 配置组装候选。

Web Speech 的音频由浏览器内部播放，通常拿不到与 `<audio>` 相同的 PCM/Analyser
数据，因此它的口型只能依赖 utterance 生命周期、边界事件或程序 fallback；
服务器/CosyVoice 音频更容易用真实能量采样同步。语音选择、播放与口型是三个
相关但不同的状态。

### 3.6 `src/ailis-chat-service.js`

`AILISDesktopChatService` 把 UI turn 转成 Gateway/Hosted 请求，管理活动 run/session、
进度事件、主动聊天、视觉附件和中断。`createGatewayProgressBridge()` 把后端事件
转换成前端可消费的进度；`toAILISPayload()` 和相关函数把运行结果规范成 UI/
Persona Surface 数据。

## 4. Electron 宿主

### 4.1 `electron/main.cjs`

这是桌面应用总接线板，包含：

- 应用、窗口、托盘、协议和桌宠尺寸/鼠标穿透生命周期。
- 本地资源、speech model、asset pack 自定义协议。
- LLM、TTS、ASR、Ollama/vLLM、运行时组件和设置持久化。
- 屏幕/窗口/区域视觉捕获。
- Gateway、TaskAgent、Runtime、控制面板和 renderer 事件广播。
- 大量 IPC handler，将 preload 暴露的能力连接到受控主进程实现。

它很大是因为它承担桌面 composition root；新增核心业务时优先做独立模块，再在
这里装配，避免继续扩大隐式全局状态。

### 4.2 `electron/preload.cjs`

preload 是安全接口面。渲染层不应直接拥有 Node 权限，而是通过
`contextBridge` 暴露严格列举的方法。审查时逐一对照：

1. preload 方法名；
2. IPC channel；
3. main 中 handler；
4. 参数校验、权限和返回值；
5. renderer 调用方。

### 4.3 桌面状态与资源

主进程将偏好、运行时目录、模型配置、窗口状态等写到受控 state 目录。运行时数据
不应提交到源码；API Key 对 renderer 的展示必须掩码化。自定义协议处理器必须做
根目录 containment，防止任意路径读取。

## 5. Agent 核心

### 5.1 `electron/ailis-task-agent-harness.cjs`

`AILISSystemTaskAgentHarness` 是系统任务的生命周期控制面：

- 按 session 选择或创建任务。
- 防止同一 session 无控制地并行执行。
- 保存 task 状态和更新时间。
- 调用实际 runner，并把结果规范成 `TASK_RESULT_SCHEMA`。
- 记录 source/evidence/output refs，支持 parent run handoff。

它不是第二个人格，也不负责把内部协议直接说给用户。

### 5.2 `electron/ailis-agent-runner.cjs`

这是模型驱动执行循环的主体，也是仓库最大的核心文件之一。其职责覆盖：

- 解析 request、provider settings、附件与 workspace。
- 构建 system/developer/context/model input。
- 控制模型调用、超时、reasoning effort、parallel tool calls。
- 接收模型 tool call，做 guard/contract/evidence 检查。
- 调用 Gateway/Runtime，记录 observation、artifact 和引用。
- 管理 token/context budget、语义压缩、checkpoint 和恢复。
- 处理 exact-answer、研究任务、结构化附件等证据充分性。
- 产生进度、审批、失败、完成或 max-steps 结果。

阅读它时不要从第 1 行连续硬啃到末尾。先用逐行页面顶部的主要符号，按
“入口 → 单次 iteration → tool execution → context update → finalization”分块，
再让测试固定每块理解。

### 5.3 `electron/ailis-gateway.cjs`

Gateway 是 Agent 与真实能力之间的统一边界，负责：

- 工具发现和直接工具暴露；
- schema/参数标准化；
- 审批、阻断、错误分类和超时；
- SSE/event、audit、usage 和 timeline；
- MCP、artifact、外部虚拟工具及结果标准化；
- 将执行 observation 以安全结构返回 runner。

Agent 不能绕过 Gateway 直接获得任意 OS 能力。

### 5.4 `electron/ailis-runtime.cjs`

Runtime 实现经契约允许的具体运行能力，包括文件、执行、补丁、上下文产物、
MCP 会话、权限请求和平台能力。它对路径做归一化/containment，对执行能力做
profile 检查，并将大输出转存为可查询 artifact，避免无限塞入模型上下文。

## 6. Context、Prompt、Memory 与 Persona

- `ailis-memory-store.cjs`：整理后的 Persona Memory、事件、affinity、daily note 和
  secret index；提供查询、更新、遗忘、清理和持久化。
- `ailis-raw-memory-ledger.cjs`：按日 JSONL 追加原始运行记录，建立 session/run 索引，
  用于重放和审计。
- `ailis-context-compiler.cjs`：按 context mode 和 section budget 编译 MemoryContext。
- `ailis-context-manager.cjs`：管理模型可见 response items、tool call/output 配对、
  图片能力、预算压缩、context package 与 checkpoint。
- `ailis-model-input-builder.cjs`：将 visible conversation、memory developer message、
  task/context 和 tool output 转成模型协议项。
- `ailis-prompt-model.cjs`：提示词片段的数据模型和装配约束。
- `ailis-persona-renderer.cjs`：把内部结果变为用户可见文字、bubble、speech、expression、
  action、emotion、gesture、gaze、duration 和 lip-sync 意图。

这些模块必须保持通道分离，详细见
[Memory、Prompt 与 TaskAgent 专册](03-Memory-Prompt-TaskAgent专册.md)。

## 7. 工具体系

工具不是单个 `execute()` 函数，而是一条链：

```text
模型提出 tool call
→ tool contract/schema
→ policy/risk/approval
→ router/capability resolution
→ runtime/platform adapter/MCP
→ normalized observation
→ artifact/evidence refs
→ ContextManager
→ 下一次模型决策或完成
```

文件、邮件、电脑操作、代码、artifact、MCP、技能安装/能力获取等模块各自实现
领域细节，但必须复用统一权限、错误、证据和审计语义。

## 8. Hosted Runtime 与 Python 后端

纯静态页面没有本地 Electron/Node 权限。Hosted Runtime 在服务器运行 Agent 核心，
通过 HTTP/SSE 提供 health、chat/run、events、tools 等能力。网页
`AILISDesktopChatService` 的 hosted 分支连接它。

`backend/` 是可选 Python/FastAPI 体系，包含 API route、service、model、配置和
静态内容。阅读时先确认当前部署到底走 Node Hosted Runtime 还是 Python route，
避免在未生效的后端修改。

## 9. 依赖与构建

- Vite 构建浏览器资源。
- Electron/Electron Builder 构建桌面包。
- Three.js、`@pixiv/three-vrm*` 负责 VRM。
- Node 内置 test runner 承担大部分核心测试。
- Python requirements 支持 FastAPI/后端能力。
- runtime pack 脚本准备 Python、Voice、ASR、Web 等可选组件。

以 `package.json` scripts 为命令真源，以 lockfile 为精确依赖真源。

## 10. 架构不变量

1. 用户只面对 Persona；内部 TaskAgent 协议不可原样泄漏。
2. 合法语义判断由模型做；确定性层只守边界和执行契约。
3. tool call 与 tool output 必须成对，压缩后也不能制造孤儿项。
4. 危险动作必须经过明确 policy/approval，不能靠 UI 文案代替。
5. Memory、可见历史、当前任务、工具证据分通道管理。
6. 每个完成声明都应能追溯到真实 observation/evidence。
7. 取消、超时和失败必须释放 in-flight、audio、speaking 和 busy 状态。
8. 桌面与 Hosted 共享核心语义，但各自的平台能力必须通过 adapter 隔离。
