# 02｜运行链路与生命周期

## 1. 桌面启动链

```text
Electron app ready
→ 注册本地资源/语音/资产协议
→ 读取桌面偏好和运行时目录
→ 创建主窗口、桌宠、控制面板等 BrowserWindow
→ preload 暴露白名单桥
→ renderer 加载 HTML + src 入口
→ 初始化 VRM / ChatTTS / SpeechProvider / ChatService
→ 按需启动 Gateway、Agent supervisor、voice/ASR/LLM runtime
→ 页面进入可交互状态
```

主入口是 `electron/main.cjs`。窗口加载的是开发 Vite URL 或构建后的静态页面。
`electron/preload.cjs` 在 Node 主进程和不可信页面之间建立受控接口。

### 启动时要区分“创建”和“就绪”

- 创建对象不等于外部服务 ready。
- Gateway/voice/LLM 可懒启动，状态查询可能触发 ensure-start。
- UI 应显示真实 readiness，而不是只根据对象存在就说可用。
- 启动失败必须被状态接口暴露，不能只写 console。

## 2. 普通对话完整链路

```text
用户输入
→ ChatTTSSystem.sendMessage()
→ 写入用户消息 DOM / history，创建 turn，设置 busy
→ AILISDesktopChatService 请求 Gateway/Hosted Runtime
→ System TaskAgent Harness 创建/恢复 session task
→ Agent Runner 编译 prompt、memory、history、task、tools
→ 模型产生回复或 tool call
→ 若无工具：形成 final result
→ Persona Renderer 生成可见 surface
→ Chat service 规范化 payload
→ ChatTTSSystem 渲染文字并选择语音
→ SpeechProvider 播放
→ VRMModelSystem 应用动作、表情和口型
→ 持久化会话，释放 turn/busy/speaking
```

### UI turn 的最小状态

- `sessionId`：连续对话/任务的身份。
- `turn`：本轮 chat/auto-chat 的取消和活动状态。
- `activeRunId`：服务端 Agent 运行标识。
- `isBusy`：界面并发门。
- 当前消息 DOM 与 message history。
- 当前 TTS/audio 和 avatar speaking 状态。

这些状态必须在完成、失败、中断和组件销毁时一致释放。

## 3. 工具任务循环

一次 Agent 运行不是一次 LLM 请求，常见循环为：

1. Harness 建立任务记录，runner 建立初始 ContextManager。
2. runner 将 system instructions、memory、visible messages、task state、工具表编译成模型输入。
3. 模型决定直接回答、搜索工具、调用工具、请求审批或继续收集证据。
4. guard 检查调用形态，Gateway 校验工具契约和策略。
5. Runtime/adapter/MCP 执行真实动作。
6. 结果被规范为 tool output；大结果可能转为 artifact/context store 引用。
7. runner 把 call/output 和 evidence refs 记入上下文与审计。
8. ContextManager 检查预算、图片支持、孤儿 call/output 和压缩需要。
9. 下一次模型调用看到观察结果并决定继续或结束。
10. finalization 检查证据、未解决字段和任务状态，生成结果包。

`maxSteps` 是安全上限，不是任务计划。到达上限意味着“明确停住并说明”，不是假装完成。

## 4. 审批链路

```text
模型提出有副作用的动作
→ contract 识别风险/权限需求
→ policy 计算是否允许、阻断或需审批
→ Gateway 产生 approval-required 结构
→ Persona Renderer 转为用户可理解的问题
→ UI 显示目标、动作和安全预览
→ 用户明确批准/拒绝
→ 批准上下文与原请求绑定
→ Runtime 执行并记录证据，或在拒绝时安全终止/改道
```

审批必须绑定具体动作，不能把一次“同意”当作后续所有危险动作的永久许可。dry-run
可以显示计划，但不能产生真实副作用。

## 5. Persona 返回链

内部结果可能包含 tool id、error code、approval state、evidence state、steps 和引用。
`ailis-persona-renderer.cjs` 把它们映射为：

- `text`：完整用户可见文字；
- `bubbleText`：角色气泡摘要；
- `speechText`：适合 TTS 的文本；
- `expression`、`action`、`emotion`、`intensity`；
- `socialTone`、`gestureIntent`、`gazeTarget`、`durationHint`；
- `ttsStyle`、`lipSync`、表面 task state。

它还会过滤内部协议、提供审批/失败/max-steps 的人格化安全表达。UI 不应绕开 surface
直接朗读内部 observation。

## 6. TTS 与口型生命周期

### 6.1 服务器/CosyVoice 音频

```text
speechText
→ candidate synthesize
→ 获得音频 blob/URL 与可选 alignment
→ AudioPlayer 播放
→ Web Audio Analyser/能量回调
→ VRM.startAudioDrivenSpeech()
→ 每帧 setLipSyncValue(energy)
→ smoothing
→ expression manager 设置 mouth preset
→ 音频 ended/error/cancel → stopSpeaking()
```

真实对齐依赖音频时钟、能量采样频率、平滑参数和 VRM expression 映射四者一致。

### 6.2 Chrome 原生 Web Speech

```text
SpeechSynthesisUtterance
→ speechSynthesis.speak()
→ start/boundary/end/error 事件
→ VRM.startFallbackSpeech() 或事件估算口型
→ 程序脉冲 + 平滑
→ end/error/cancel → stopSpeaking()
```

Chrome 内部 TTS 一般不向页面提供 PCM，因此不能和音频文件一样做真实能量同步。
若出现“嘴在动但不跟字”，应承认这是 fallback 的物理限制，再优化 boundary/时长估算；
不要把随机脉冲描述成音素级对齐。

### 6.3 口型排错状态表

| 现象 | 首查 |
| --- | --- |
| 完全不张嘴 | speaking 是否开始；VRM expression manager；最大开口；是否被情绪表情阻断 |
| 说完仍张嘴 | ended/error/cancel 是否都调用 stop；旧 turn 是否泄漏 |
| 口型有节奏但不对字 | 是否走 Native fallback；是否缺 alignment/PCM |
| 音频对但嘴滞后 | analyser 回调、帧时钟、smoothing 过大、音频启动先于 speaking |
| 换语音后失效 | voice id 是否仍存在；voiceschanged；candidate 是否真的选中 |

## 7. 主动聊天与自动机会

`ChatTTSSystem` 有 auto-chat timer 和 proactive state；chat service 会生成主动机会的
system/developer message，模型决定是否自然发起。主动聊天仍必须复用正常 turn、
memory、Persona 和 TTS 生命周期，不能绕过 busy/interrupt 门。

## 8. 中断链

用户中断时应发生：

1. UI 标记当前 turn cancelled。
2. 停止/取消 audio 和 `speechSynthesis`。
3. `ChatService.abortCurrentTurn()` 用 runId/sessionId 通知宿主。
4. Gateway/runner 取消在途模型或工具（能力允许时）。
5. 丢弃迟到的 progress/final event，避免污染下一轮。
6. VRM `stopSpeaking()`，UI 释放 busy。
7. Harness 保留可解释的取消状态或 checkpoint。

只在 UI 隐藏 loading 不算真正中断。

## 9. Context 与 checkpoint 生命周期

ContextManager 接收 message、tool call、tool output、图片和上下文包。随着运行增长：

- 截断过大的单个 tool output；
- 将陈旧输出压缩为带引用摘要；
- 保留近期可见消息和必要 call/output 对；
- 在模型不支持图片时剥离图片而保留文字提示；
- 建立 dropped-items manifest 和 output refs；
- 必要时做语义压缩；
- `toCheckpoint()` 保存 history version、token info、reference item 和 items；
- 恢复时 `fromCheckpoint()` 重建一致历史。

压缩是信息管理，不是删除证据真相。完整大输出应留在 artifact/output store 可查询。

## 10. Memory 生命周期

```text
对话/任务/工具事件
→ Raw Memory Ledger 追加原始可审计条目
→ session/run/day 索引
→ 记忆整理策略识别稳定偏好、关系、事实、任务线索
→ Memory Store 更新 block/event/daily note/affinity
→ 新一轮按用户消息和历史构建 retrieval query
→ Context Compiler 选择、脱敏、按 section budget 编译
→ Model Input Builder 作为 developer memory context 注入
```

并非所有原始事件都应永久成为 Prompt Memory；敏感值和短暂任务噪音尤其要隔离。

## 11. Hosted 网页链路

```text
GitHub Pages/阿里云静态页面
→ 浏览器加载 Test/ 或构建资产
→ Hosted API health/readiness
→ HTTP 创建/继续 run
→ SSE/轮询接收 progress、approval、final
→ 服务器内 Harness/Runner/Gateway/Memory/Tools
→ Persona Surface 返回网页
→ 浏览器 Web Speech 或服务器 TTS + VRM
```

网页部署成功要分别验证“静态页面 200”“API health 200”“真实 Agent turn 成功”
和“TTS/口型真实播放”，只看首页 200 不够。

## 12. 失败分类

| 类别 | 例子 | 正确处理 |
| --- | --- | --- |
| 配置缺失 | API Key、邮箱、运行时未安装 | 明确 `needs_config`，给下一步，不伪装工具故障 |
| 需审批 | 写文件、发邮件、系统操作 | 返回绑定动作的 approval |
| 权限阻断 | 路径越界、profile 不允许 shell | `blocked`，保留审计 |
| 工具失败 | 网络、解析、进程退出码 | 标准化 error/observation，允许模型恢复 |
| 模型失败 | 超时、协议无效 | 有界重试/降级，避免无限循环 |
| 证据不足 | 工具成功但未回答问题 | 继续收集或诚实停止 |
| 用户取消 | interrupt/cancel | 释放所有在途状态，不朗读迟到结果 |
| 达到预算 | max steps/context | checkpoint + Persona 安全解释 |
