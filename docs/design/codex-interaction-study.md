# Codex 交互设计系统研究：从聊天窗口到可检查、可干预的任务工作台

主要对象是 Codex 桌面任务体验；CLI、IDE 和 App Server 仅用于补充行为与协议依据。AILIS 对照对象为独立工作树 `D:\AILIS-worktrees\task-interaction-20260913` 的任务交互预览，不代表已发布安装包。

## 1. 核心结论

Codex 最值得学习的不是“白色聊天界面＋几个图标”，而是一种任务协作方式：**用对话表达意图和解释判断，用结构化记录展示执行事实，用相邻工作区检查成果，用有明确作用范围的控件干预任务。**

它同时处理四个问题：

1. **我知道它在干什么。** 关键进展可以读懂，底层证据能够展开，不必一直盯日志。
2. **我能改变接下来发生的事。** 调整当前任务、安排下一轮、停止执行、回答问题、批准操作是不同动作。
3. **我能检查它实际做了什么。** 回答、工具输出、文件差异、图片和网页不是同一种文本。
4. **我不必被一个任务困住。** 会话导航、运行状态、工作目录、权限和成果查看各自有边界。

这是对官方能力和界面证据的设计归纳，不是 OpenAI 公开的一套内部设计宣言。[^1][^2][^3][^4]

对 AILIS 的直接判断：上一轮预览虽然补齐了若干功能，但还偏向“把内部任务记录展示给用户”。删提示、缩小卡片只解决表层问题；真正需要对齐的是**阅读顺序、信息主次、操作语义、成果工作区，以及导航与执行的解耦**。

## 2. 证据边界：哪些是事实，哪些仍需实测

资料与代码的核验基准日为 2026-09-14。

本报告使用三类证据：

- **官方事实**：桌面产品文档说明的行为；公开 App Server 文档说明的协议。协议支持某种状态，不等于桌面会把每个字段显示成一个标签。
- **界面观察**：参考截图中的完成态。截图能证明布局和可见入口，不能证明点击后的效果、追加时机、取消延迟或全部平台行为。
- **本地代码事实**：AILIS 预览的渲染与会话控制实现。由代码推断的可用性、性能风险，不冒充用户测试结论。

本机应用包元数据显示 `OpenAI.Codex 26.908.4834.0`。官方文档中部分页面已统一使用 ChatGPT desktop app 的名称，并用 app、web、CLI、IDE 区分能力；本报告只将明确属于桌面/Codex 的部分用于直接比较。账号、灰度发布、操作系统及连接的 host 版本都可能影响可用性。[^16]

本报告**没有取得 Codex 私有桌面前端源码，也没有对全部交互做现场点击验收**。因此不能宣称像素级复刻、所有状态实测通过，或知道其内部组件、数据库、虚拟列表实现及性能 SLA。

## 3. 系统的对象模型：先把“是什么”分清楚

公开 App Server 明确定义 Thread、Turn、Item：会话包含轮次，轮次包含用户消息、助手消息、命令、工具、文件变更等项目。项目与工作目录属于另一层上下文；不能把所有对象都叫作“任务”。[^1][^5]

| 对象 | 回答的问题 | 不应该混淆为 |
| --- | --- | --- |
| 项目 / 工作目录 | 在哪一份文件上工作？ | 会话历史、虚拟机、权限边界 |
| 会话 Thread | 围绕哪个持续上下文交流？ | 单次模型请求、一个 OS 进程 |
| 轮次 Turn | 这一次请求及其后续工作是否结束？ | 一次工具调用、整个长期目标 |
| 项目 Item | 哪条消息、哪个命令或哪次改动正在变化？ | 任意一行日志、完整最终回答 |
| 成果 / 资源 | 可以检查哪个文件、图像、页面或输出？ | 模型嘴里提到的路径 |
| 环境 / Host / Worktree | 实际在哪台机器、哪个 checkout 执行？ | 模型名称、侧栏分组 |
| 权限请求 | 哪个具体动作需要授权？ | 普通追加消息、永久开启全部权限 |

可以用最小结构理解它：

```text
项目 / 执行环境
  └─ 会话
      ├─ 轮次 A
      │   ├─ 用户请求
      │   ├─ 助手进展 / 命令 / 工具 / 文件变更 / 中途输入
      │   └─ 最终回答 + 可检查成果
      └─ 轮次 B

界面当前查看哪个会话，是选择状态；哪个轮次仍在执行，是运行状态。
```

**设计推论**：如果“用户正在看哪里”被写成“执行器只能拥有哪里”，后台任务就会锁住整个产品。反之，只做多会话侧栏、却让所有执行都隐式使用同一个全局 cwd，也只是表面多任务。

## 4. 空间布局：每个区域承担不同工作

### 4.1 参考截图能够确认的设计

截图里的信息层级非常明确：顶部是当前任务标题，中间是主要对话，答案后是一张紧凑的已编辑文件卡片，卡片提供差异数量和审核入口；复制、朗读等次要操作弱化显示；底部是持续可用的输入区，包含附件、权限、模型/推理设置和发送入口。

文件卡片没有铺满原始 diff，也没有常驻显示会话 ID、字节数、快照解释和回执流水。它回答的是“发生了什么，以及去哪里看”，而非在聊天正文里承担整个文件查看器。

截图中的“目标已停滞”栏需要特别区分：官方长期工作文档说明，设置 goal 后才会在输入区上方出现目标进度控件。它不是每次普通对话都需要复制的常驻横条。[^6]

### 4.2 更完整的工作区分工

官方桌面功能提供聊天旁的文件/文档预览、代码审核以及浏览器；侧栏支持会话组织，键盘命令支持面板、文件树、终端等入口。[^3][^4][^5][^9]

| 区域 | 主要职责 | 应避免 |
| --- | --- | --- |
| 侧栏 | 项目、会话、未读/待关注工作的定位 | 用进入会话代替重启任务 |
| 对话主区 | 用户意图、公开进展、结论与成果入口 | 全量调试面板、重复状态教学 |
| 过程展开区 | 命令、工具、原始输出、执行证据 | 把有价值的进展也全部藏起来 |
| 相邻工作区 | 阅读文件、查看 diff、预览网页和文档 | 每检查一个成果都强制离开对话 |
| 输入区 | 新请求、当前调整、后续队列、附件和设置入口 | 忙碌时只剩停止，不能交流 |
| 情境控件 | 问题、审批、排队、长期目标 | 无论状态如何都显示全部控件 |

这里的关键是空间连续性：对话里指出一个问题，旁边检查相应证据，再带着具体位置反馈，而不是在“聊天 → 弹窗 → 关闭 → 回忆文件位置 → 再提问”之间往返。

### 4.3 外观不是固定主题

Codex 支持主题、界面字体和代码字体等设置。因此白底、某一种灰色或某个字号不是它的系统本质。[^10] 应学习的是层级、密度、对齐、点击目标和可读性；没有来源支持的精确间距和动画时长，不应包装为 Codex 标准。

## 5. 执行反馈：不是“越少越好”，而是分清四类信息

公开协议区分助手消息的 `commentary` 与 `final_answer`，同时有命令/工具 Item、计划更新、错误和权限请求。这为分层展示提供了基础，但不规定所有客户端必须采用同一种视觉组件。[^1]

### 5.1 公开进展：解释工作为什么发生变化

有价值的进展应当让人理解新增事实、决策或阻塞。例如：

> 已定位到输出转换丢失错误信息；接下来检查进程启动失败是否也走这条路径。

这与“运行中”“正在处理”“已接收任务”不同。前者减少不确定性，后者通常只是重复已知状态。

这些是公开可读的工作说明，**不是模型隐藏思维链**。不能为了“看起来透明”暴露原始内部推理，也不能用一个定时器制造没有依据的进度句子。

### 5.2 执行事实：给人可查的证据

命令记录可以包含 command、cwd、状态、stdout/stderr、退出码和耗时；工具记录包含身份、结果与错误；文件变更具有类型和 diff。[^1] 用户需要时应能看到这些事实，而不必依赖助手事后转述。

“命令没有 stdout”与“进程创建失败”不是同一种状态。可以压缩展示，但不能把错误语义转换掉。对于错误 267，短摘要可写“工作目录无效，命令未启动”，详情仍须保留原始错误、cwd 和失败阶段。这是 AILIS 的设计建议，不是对 Codex 已覆盖某个特定 Windows 错误的实测声明。

### 5.3 最终回答：承担结论，不复述全部流水

回答应说明结果、验证情况和剩余边界。文件变化由成果入口补充，命令细节由执行记录补充；不要把正文写成另一本操作日志。

反过来，不能只丢下一张“任务完成”卡片，要求用户打开所有工具结果才能知道到底完成了什么。

### 5.4 需要用户行动：优先级高于普通过程

缺少信息、等待审批、不可恢复的失败与普通运行必须分开。App Server 的会话状态可以携带 `waitingOnApproval`；桌面通知也分别支持任务完成、审批请求和问题提醒。[^1][^7]

**建议的信息梯度**：结论和需要处理的问题在前；有意义的进展可见；重复的执行细节可展开；ID、原始元数据和诊断日志按需查看。折叠是呈现策略，不能成为丢证据的理由。

## 6. 运行中输入：Steer、Queue、Stop 不是同一套“追加”

这是最容易照错的部分。Steer 与 Queue 的定义来自输入文档；中断与请求响应来自 App Server；侧聊来自长期工作文档。下表按作用范围归纳，而非照录某个菜单：[^1][^2][^6]

| 动作 | 意图 | 作用范围 |
| --- | --- | --- |
| Steer，调整当前任务 | 补充条件、改变当前方向 | 当前仍在运行的轮次 |
| Queue，排到下一轮 | 当前工作结束后再做另一件事 | 后续轮次 |
| Stop，中断 | 不再继续本轮工作 | 指定正在执行的轮次 |
| 回答问题 | 补上某个澄清请求所需信息 | 对应的问题请求 |
| 批准 / 拒绝 | 授权或拒绝具体行动 | 对应的权限请求 |
| 新会话 / 侧聊 | 另开上下文，或在不打断主任务时询问状态 | 不应偷偷变成当前任务的调整 |

### 6.1 Steer 的核心是“目标轮次明确”

App Server 的 `turn/steer` 请求指定 `threadId`、`expectedTurnId` 和 `input`。如果没有活动轮次或预期 ID 不匹配，请求失败；它不会产生新的 `turn/started`。该入口不允许顺便覆盖本轮 model、cwd、sandboxPolicy 等参数。[^1]

示意：任务 A 正在排查启动错误，此时补充“只修工作目录，不改提示词”，属于调整 A，而不是新任务 B。

请求被接收不证明它已经影响某次模型决策，更不保证已经运行中的外部命令能被立即撤销。界面不能把回执写成“已经执行”。官方接口也没有承诺固定多少毫秒内调整生效。

### 6.2 Queue 是可编辑的后续工作

桌面端可在 General 的 Follow-up behavior 中设置默认使用 Steer 或 Queue；排队消息显示在输入区上方，可编辑、重新排序、发送或删除。设置里还显示临时使用另一种行为的快捷方式。[^2][^10]

因此“在输入框上方看见一条消息”并不能直接推断为“当前轮次已接受这条消息”。它可能仍然只是下一轮的可编辑队列。

CLI 的 Enter/Tab 行为是 CLI 文档明确规定的；不能不加区分地套在桌面端，尤其桌面发送行为可配置。[^2]

### 6.3 内部状态可以细，外部反馈不必碎

AILIS 可以记录发送中、落盘、待纳入、已纳入、未处理等状态，以处理重连、重复发送和故障。但无需给每条正常成功消息挂一排徽章。

正常路径只需让用户确认：消息还在、是本轮调整还是下一轮工作、是否发生异常。只有存在较长等待、发送失败或目标轮次变化时，才强化说明并给出可用动作。

AILIS 现有 `clientMessageId` 用于幂等回执，有实际价值；它属于 AILIS 的实现选择，不能说它是官方 `turn/steer` 示例中的必填字段。

### 6.4 中断有两个时刻

App Server 对 interrupt 请求返回成功后，本轮最终状态才变成 `interrupted`。[^1] 产品应区分“停止请求已发出”和“执行已停止”；不能一点击就把所有进程画成已结束。

停止并不是撤销文件、取消已经提交的外部动作，也不是恢复整个工作目录。停止后尚未处理的输入应有明确去处，不能默默丢弃或未经用户选择自动执行。最后一点是 AILIS 的可靠性要求，不是对 Codex 所有异常路径的现场验证。

## 7. 成果体验：检查、评论、修改构成闭环

### 7.1 聊天卡片只是入口

参考截图里的编辑卡片负责简洁汇总，官方文档则说明桌面有独立审核窗格及文件查看器。[^3][^4] “有查看按钮”并不等于实现了这一体验：如果打开的是遮住对话的模态框，阅读与反馈仍然被割裂。

适合学习的闭环是：**看到结论 → 定位相关成果 → 检查细节 → 指向具体位置提出意见 → 再检查修订结果。**

### 7.2 文件差异至少要说清比较范围

Codex 审核窗格提供 Unstaged、Staged、Commit、Branch 和 Last turn 等范围。默认的仓库差异可能包括人工或其他任务造成的变化；官方排错文档专门提醒，若只想看上一轮，应切到 Last turn。[^3][^16]

这意味着不能把整个 `git diff` 标成“本次 AI 修改”。以下三个对象也不同：

- 本轮中被观测到的某次文件写入快照；
- 本轮多次修改聚合后的净差异；
- 当前整个仓库的未提交差异。

App Server 有 `turn/diff/updated`，提供本轮文件变更的聚合 unified diff；这仍不意味着所有经 shell、外部程序或其他任务改变的文件都能自动被完美归因。[^1]

对于非 Git 项目，也必须明确当前能力是“受控写入快照”还是“全目录变更监测”，不能沿用 Git 审核名称却偷偷改了含义。

### 7.3 “审核”有三种不同动作

1. **打开审核窗格**：人查看差异。
2. **运行 `/review`**：Agent 检查改动并给出问题，官方说明这一动作不直接修改工作树；可在当前会话或配置的独立会话中运行。
3. **要求修复审核意见**：再次明确提出更改请求。

窗格里的行内评论也是定位反馈；应在聊天中发送处理这些评论的要求，而不是默认评论一保存就执行代码修改。[^3]

### 7.4 撤销能力必须有明确边界

Codex 的审核工作流提供按文件、部分差异等粒度处理 Git 变更。截图也出现了撤销入口，但不能据此推出“一键可靠地撤销整个任务所有副作用”。[^3]

对 AILIS，若尚不能检测用户在任务之后的编辑，就不应复制一个看起来同样强大的全局撤销按钮。可以先做好只读检查；未来提供撤销时，必须指明对象、比较基线、冲突判断和恢复能力。公开协议中旧的 `thread/rollback` 处理会话上下文且已标为弃用，更不能拿它当文件回滚接口。[^1]

### 7.5 图片、文档和网页不是路径字符串

桌面文档查看器支持在聊天旁检查文档、幻灯片、表格及 PDF；特定内容可通过选择和批注提供局部反馈。浏览器也支持选择元素或区域、写评论，再要求处理。[^4][^12]

AILIS 的目标不应止于“Markdown 把图片画出来”，而应包含：持久资源引用、可打开的原图、失败占位、图像与对应轮次的关联，以及反馈时能准确指向图像/文件位置。以上是迁移建议；缩略图尺寸、放大动画、图片缓存策略不是已核验的 Codex 内部规范。

## 8. 输入区：它是任务控制入口，不是独立控制台

参考截图把附件、权限、模型/推理设置放在输入区底部；它们与下一条请求有关，因此在此处可访问。并不需要把每项配置的说明长期展开。

官方资料还说明图片输入、语音听写、模型选择快捷键、历史输入恢复及发送设置等能力。[^2][^9][^10][^11]

应该保留的共同原则：

- 附件能被看见和检查，而不是只显示“已添加上下文”。
- 当前输入的语义明确：发送新请求、调整当前工作，或排到下一轮。
- 草稿是用户正在编辑的内容，失败不应让它消失。
- 模型与权限显示真实的当前选择；改变设置不等于已经改变正在执行的轮次。
- 停止、发送和回答问题不能因焦点或状态竞争相互误触。
- 输入区不承担运行日志和长篇帮助说明；详细设置使用独立入口。

语音尤其要区分：**听写**先转换成可编辑的输入文本；**实时语音会话**是能够谈进展、补信息和协调任务的另一种交互，并受可用性和权限限制。[^2][^13] 不能把 TTS 是否播完当作任务是否完成，也不能认为语音流和文本任务必然具有相同的取消范围。这两条属于 AILIS 的状态设计要求。

## 9. 会话、导航和运行：离开页面不等于停止工作

官方产品支持组织多个会话、单独任务结果、后台工作和待关注状态；长期工作也支持在不打断主任务时使用侧聊了解进展。[^5][^6][^7]

由此得到的产品原则是：**查看状态与执行状态必须解耦**。打开旧会话、查看文件、切换面板不是隐含的开始、停止或授权操作。

对 AILIS 的最小实现要求并不等于立刻增加任意并发：即使只允许一个执行器工作，用户仍应能够只读浏览其他历史，再返回运行中的任务。若要在另一会话启动第二个任务，可以单独给出资源或并发限制，不能连看都不让看。

恢复还应区分：

- 恢复历史显示；
- 重新订阅仍存活的后台任务；
- 对已结束任务发起新一轮；
- 对状态未知任务进行故障恢复。

App Server 提供不启动执行的已存会话读取、会话状态通知及分页列表。[^1] 这为分离阅读和执行提供依据，但并不证明 Codex 在每一种崩溃或网络断开情况下都无损恢复。

草稿、滚动位置、文字选择、展开状态和正在检查的文件，是容易被忽略的交互状态。对 AILIS，应将它们列入验收；不能因一个 token 到来或后台状态刷新而不断丢失。这是建议的测试要求，不是对 Codex 未公开前端机制的推断结论。

## 10. 注意力管理：少打扰和可控并不矛盾

官方通知设置区分完成通知、审批和问题提醒，完成通知可设为不提醒、仅后台提醒或总是提醒；Activity 在可用时集中展示未读、运行中和等待响应的任务。[^7]

可提炼为三层：

1. **我正在看这个任务**：在原位置更新，不需要每一步再弹一次通知。
2. **我暂时不看这个任务**：侧栏状态、未读或完成提醒帮助重新定位。
3. **任务必须等我处理**：将问题或审批提到足够醒目的位置，并保留明确入口。

“正常时安静，异常时明确”是这里的分析结论，不是说 Codex 完全没有冗余提示或永不通知过多。

AILIS 尤其应避免重复播报：同一个完成事件同时出现正文、横条、toast、桌宠长句和语音，不会增加可信度，只会增加打断。多个显示渠道可以共享同一状态，但需要各自的注意力策略。

常态文字可以精简，异常事实不能精简掉。相比每次教用户“这里可以追加”，更有价值的是在一次失败时明确说：“消息没有发送成功，原文已保留。”

## 11. 权限与安全：不是把所有提示都删掉

官方文档区分 sandbox 的执行边界与 approval 的授权时机。权限选择、具体动作审批以及操作系统自身权限也不是同一层。[^8]

好的交互让用户理解“这次批准什么”，而不是遇到问题就建议“打开管理员权限”或“切到完全访问”。命令、文件或网络授权应绑定明确对象及作用范围；App Server 的相关请求携带会话、轮次、Item 或 request ID 等标识，答复不能错投给另一个请求。[^1]

其中一条重要边界是：**用户表示希望任务继续完成，不等于授权扩大文件、网络或系统权限**。长期 goal 也不应该隐含扩大权限。[^6][^8]

在体验上，应压缩的是无决策价值的重复提示，而不是审批必要信息。至少要能辨认对象、动作、范围及允许/拒绝的后果；已经失效的请求不能继续表现为可以批准。

## 12. 环境与上下文：避免“看起来隔离，实际共用”的误导

### 12.1 不同会话、不同源码版本，不等于不同机器环境

Codex 的 worktree 提供独立 checkout，但共享 Git 仓库元数据。它不是自动分配一整套独立的操作系统、Docker daemon、端口、代理、缓存和外部服务。[^5][^14]

因此两份不同版本的程序仍可能争用同一端口、同一后台服务、同一模型额度或同一文件路径。这是运行环境层的可能性，不能把“开了新任务”包装成“完全隔离”。

UI 应让工作目录、host、本地/工作树选择和权限在相关位置可以核对；它们不必每条消息都重复，但发起或迁移工作时必须能知道将在哪里执行。官方 Handoff 和 Worktree 工作流将会话与其代码状态的转移作为显式操作。[^14]

### 12.2 可见历史不等于每次发给模型的全部上下文

官方提供会话读取、上下文压缩项目和单独的本地记忆控制；本地 Codex 记忆与 ChatGPT web 记忆也有不同存储和控制。[^1][^17]

重要团队规则应保存在明确的项目指导中，记忆是回忆辅助；桌面可分别控制某个会话是否使用记忆、是否贡献未来记忆。[^17]

对 AILIS，这意味着聊天记录、执行证据、用户偏好、模型本轮上下文与跨会话记忆需要有明确的数据职责，不能全部由一个“消息字符串”承担。界面折叠工具输出本身不等于减少模型输入，也不能证明缓存命中率会提高；后者必须测量真实 usage。

## 13. 键盘、可访问性与细节：连续工作时才会显现的差距

Codex 提供命令菜单、文件搜索、会话内查找、历史输入恢复、面板切换、模型选择和“下一个需要关注的任务”等快捷入口；快捷键可以在设置中搜索和修改，并区分操作系统。[^9][^10]

Windows 文档中的几个例子：`Ctrl+Shift+P` 打开命令菜单，`Ctrl+F` 在会话中查找，`Ctrl+P` 搜索文件，`Ctrl+J` 切换底部面板，`Ctrl+Alt+A` 跳转下一项待关注的 Codex 任务。它们体现的是“高频工作不用反复找按钮”，不意味着 AILIS 必须逐个复制这些组合。[^9]

对 AILIS 应检查：中文输入法组合态不误发送；图标有可访问名称；键盘可以打开成果并返回原位置；代码可选择和复制；窄窗口和大字体不遮住发送/停止；新输出不夺走正在阅读旧消息的用户。没有相应实测时，不能称“完整无障碍已达到 Codex 水平”。

动效也应服务于定位：状态发生变化时让人认得原对象，而不是全区重排。无需复制不明来源的动画曲线，也不应以持续闪烁替代真实进展。

## 14. 长期工作与多端：同一任务的延伸，不是额外刷屏入口

长期目标、定时工作和远程查看解决不同问题。goal 表示持续追求的结果；定时任务决定何时返回工作；Remote 让另一个设备查看、批准和引导连接主机上的任务。[^6][^15][^18]

官方定时任务区分回到当前会话继续使用上下文，和每次创建独立会话；桌面本地任务仍需要主机可用。Remote 也明确由连接的电脑实际运行任务，并要求主机保持在线。[^15][^18]

可迁移的设计原则：

- 不要用“模型正在输出”表示所有后台工作状态。
- 计划暂停、等待输入、主机离线和任务失败必须可区分。
- 多端是同一任务的多个读写入口，不应各自伪造状态。
- 长期工作不是每十分钟向聊天里复制一次长指令和相同状态；通知应与新的结果、失败或需要处理的问题相关。

最后一条是注意力管理建议，不是对所有 Codex 定时任务默认通知行为的统一声明。这些扩展也不应挤占 AILIS 当前最基础的执行反馈与成果检查优先级。

## 15. AILIS 预览的实际差距：不是只差几个样式

以下只针对 2026-09-14 检查到的独立预览源码。路径行号是定位入口，文件后续变化时应按函数名复核。

| 现状与代码证据 | 对体验的影响 | 应学习的设计 |
| --- | --- | --- |

这些问题不表示现有工作全部无用。已有持久回执、精确轮次标识、停止确认、原始输出引用、受控文件快照和图片记录，是可靠交互的基础。**应保留可靠性机制，重做不合理的状态呈现与区域分工。**

先前回归测试通过，只能证明测试覆盖到的功能行为；不能证明提示密度、阅读连贯性、长会话表现或用户体验已经与 Codex 等价。

## 16. 对齐策略：先对齐语义，再对齐布局，最后对齐细节

以下是建议顺序，不是本报告已实施的改动。

### P0：先解决会误解、会丢信息、会困住用户的问题

1. 明确会话、轮次、Item、成果、环境的职责，保留现有 EXEC 与模型决策权。
2. 整理公开进展、执行事实、最终回答和待响应请求的独立呈现。
3. 按发生顺序展示中途输入；区分本轮调整与下轮排队。
4. 把查看其他会话从启动执行中拆开，不再因任务运行禁止只读浏览。
5. 保留发送失败、停止未确认、原始执行错误与未知恢复状态，不做“看起来已完成”的美化。

### P1：形成真正的检查与反馈工作区

1. 文件、diff、原始输出及图像放进可持续查看的相邻区域。
2. 文件入口按明确范围聚合，区分本轮快照、本轮净差异和仓库差异。
3. 局部反馈携带文件、行号或资源位置；不能把“评论”自动升级成写入授权。
4. 输入区只保留当前任务需要的操作；队列、审批、目标按情境出现。
5. 保持草稿、阅读位置、选择、展开项和查看资源的连续性。

### P2：补齐高频效率与规模表现

再考虑命令菜单、查找、快捷键映射、侧栏待关注管理、通知策略、长历史加载和多端延伸。是否加入完整 Git 操作、实时语音协调或长期目标，要看 AILIS 的产品范围，不能为了外观相似把所有功能同时搬进来。

不需要为此新增 Persona/TaskAgent 双模型链路，不需要改 INSTRUCTION、放松参数校验或替换 EXEC；不应为了展示进度额外调用模型。公开进展从已有助手输出产生，执行事实从真实事件产生，UI 负责正确展示。

## 17. 验收方法：测试用户是否能完成动作，而非截图是否像

以下是拟议的 AILIS 验收清单，不是已经执行的 Codex 测试结果。

### A. 正常工作与阅读

1. 只问一句常识：没有空的工具面板、假计划或无意义任务教学。
2. 执行多个工具：公开进展与事实记录可区分；不必展开全日志才知道新发现。
3. 出现关键判断变化：它出现在相应时间位置，不被后来的摘要抹掉。
4. 阅读旧消息时继续产生输出：不强制把滚动位置拉回底部。
5. 选择代码并复制时继续流式更新：文字选择和复制内容不损坏。

### B. 输入与干预

6. 本轮运行时补充限制：进入正确的活动轮次，消息位置可辨认。
7. 安排下轮任务：仍在队列，可改、可删，不宣称已被当前轮次执行。
8. 发出调整时原轮次恰好结束：不静默改投、不丢稿；明确说明采取的处理方式。
9. IPC 回执丢失后重试：没有重复执行同一用户消息。
10. 停止：先显示停止中，真实终止后才结束；文件不会被暗中回滚。
11. 等待问题或审批时切换会话再回来：仍能定位同一个请求，过期回复不会误授权新动作。
12. 中文输入法确认候选字：不会误触发发送或批准。

### C. 成果检查

13. 同一文件改三次：本轮汇总与每次快照有清楚关系，不给人三个不同最终文件的错觉。
14. 工作目录有人工修改：不会全算成 AI 本轮成果。
15. 从回答打开文件/diff，再指向某一处提问：不用关闭成果并重新描述整个位置。
16. 图片能预览与打开；资源失效时有明确失败状态，而不是空白区域。
17. 大文件、二进制、未捕获内容：如实声明不能展示的部分，不伪造精确 diff。

### D. 故障、持久性与规模

18. 进程因 cwd 无效而未创建：短摘要保留失败阶段，详情能查原始错误，不显示为成功空输出。
19. 一个会话运行时可查看另一会话；阅读导航本身不触发执行。
20. 窗口刷新/应用重开：先恢复记录并核验任务状态，不自动重做有副作用操作。
21. 存储写入失败或状态未知：不给虚假成功回执，也不把恢复责任藏在普通日志里。
22. 大字体、窄窗、键盘操作：输入、停止、错误动作和成果入口仍可用。
23. 多千条 Item 的历史：测量首次加载、单次增量更新和切换时的响应，不能只用四张短对话截图验收。
24. 同一任务在聊天、桌宠、语音三个入口出现：状态一致，通知不重复轰炸。

### 指标应怎么量

应记录发送后本地确认耗时、首个执行事件耗时、首条有意义进展耗时、停止请求至真实结束耗时、草稿丢失次数、重复执行次数、错误类型保真率，以及打开指定改动并提出局部反馈所需操作数。

性能统计要区分前端、IPC/事件传输、模型服务和命令运行耗时。模型首 token 慢不能用更快的假进度条掩盖；也不能用总任务耗时证明前端刷新很慢。这里不设置冒充 Codex 官方标准的固定毫秒目标。

用户测试还应问三个问题：刚才知道它在做什么吗？能分清新消息会影响哪一轮吗？能独立查出实际改了哪些内容吗？这比“界面看着像不像”更能验证是否学到了交互系统。

## 18. 尚未确认与最终判断

仍需进一步现场观察的内容包括：不同状态下桌面端发送/停止控件的精确位置与动画；当前账号的默认追加模式；队列遇到异常终止的全部分支；多窗口焦点与草稿行为；跨平台无障碍；大历史性能；某些审批、语音与多端功能的灰度差异。

这些未知项不影响已经明确的结构性结论，但禁止把报告当成完整私有设计规范直接逐像素实现。

最终判断：**Codex 的简洁来自职责分清，而不是把信息做少。** 主区负责对话和判断，执行记录负责证据，工作区负责检查，输入区负责意图，情境控件负责需要处理的状态。AILIS 应优先对齐这些边界及其连续体验；单纯添加更多提示、更多卡片，或把一切折叠成“思考中”，都会继续偏离这个目标。
